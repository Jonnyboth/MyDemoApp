# Checklist de Auto-Revisión — Antes de Reportar Terminada la Construcción

- [ ] `grep -rn "import requests" tests/ --include="*.py"` no devuelve nada fuera de `tests/core/http_client.py`.
- [ ] Ningún `assert` dentro de `tests/tests/**` compara directo contra `response.json()`/`response.text` — todo pasa por una función de `tests/utils/assertions.py`.
- [ ] El escenario está escrito **una sola vez**, en `tests/tests/component/test_<KEY_SIN_GUIONES>_<funcion>.py` (o en `tests/tests/e2e/` con código propio si es un flujo encadenado), marcado `@pytest.mark.component`.
- [ ] Si el diseño lo clasificó como smoke y/o regression, `tests/tests/smoke/test_smoke_<dominio>.py` y/o `tests/tests/regression/test_reg_<dominio>.py` lo traen vía `from tests.component.<modulo> import <función>` — **nunca** una copia del cuerpo de la función. Si ya existe un archivo para ese dominio (con cualquier sufijo, ej. `_manager`), reutilízalo — nunca crees uno nuevo con otro sufijo.
- [ ] Los casos de borde puro (límites numéricos, valores extremos sin valor de negocio) NO se promovieron a `smoke/`/`regression/` — quedan solo en `component/`.
- [ ] Los payloads se arman con un builder (Faker por debajo) o, si son triviales (1 campo), un dict inline — nunca un payload fijo repetido en más de un test salvo que el diseño lo pida explícitamente (ej. un ID fijo para forzar un 404).
- [ ] Si se agregó un host nuevo: `tests/.env.example` tiene las 3 líneas `{SERVICE}_{TIER}_BASE_URL` y `config/environment.py:_DEFAULT_BASE_URLS` tiene el default correspondiente.
- [ ] Se corrió el/los test(s) nuevo(s) puntualmente, desde `AutomationBackend/tests/` (`ENV=qa pytest tests/component/test_<KEY>_<funcion>.py -v`, y si se promovió, también `pytest tests/smoke/` / `pytest tests/regression/`) y el resultado es el esperado por diseño (pasa en verde, o falla intencionalmente si es un caso negativo que documenta un bug conocido).
- [ ] El archivo `component/` sigue la "Anatomía obligatoria" del `system.md`: encabezado en orden docstring (1 línea) → imports → constantes/JSON; y en cada función `test_*`, separador de 84 `#` antes de los decoradores, `@pytest.mark.scenario_name(...)` presente, y `assert_status_code` como **primera** aserción del cuerpo (nunca después de otra aserción).
- [ ] `tests/docs/MODULES.md` se actualiza si se agregó un archivo/capa nueva, para que el índice siga reflejando la realidad del framework.
- [ ] Ningún `service` nuevo assertea por su cuenta (salvo un caso de autenticación tipo `AuthService.login`, donde validar el status es parte intrínseca de obtener el token).
- [ ] Ningún `service`/`builder`/`test` nuevo agrega lógica de retry manual — eso es exclusivo de `core/http_client.py` y solo para `GET`.
- [ ] Si el test implementa un paso de un Caso de Prueba de AIO Tests, su nombre sigue `test_<KEY_SIN_GUIONES>_<descripción>` (ej. `test_SIM_TC_12_create_user`) y el campo `automationKey` de ese TC en AIO Tests quedó actualizado apuntando al nombre/ruta reales.
- [ ] Si alguna validación del TC no coincide con el comportamiento real de la API (verificado con curl), el test la automatiza igual pero marcada `@pytest.mark.xfail(reason=..., strict=True)` — nunca se omite en silencio ni se fuerza a pasar con un assert distinto al que pide el TC.
- [ ] Todo escenario (y cada caso de un `parametrize`, vía `pytest.param(..., marks=pytest.mark.scenario_name(...))`) lleva `@pytest.mark.scenario_name("<KEY-TC> <validación principal>")` — ej. `"SIM-TC-12 Create user age value Mayor 100"` — y se ve tanto en consola (📌) como en el reporte HTML al correr el test.
